## 五行思路（2026-10-11，原样保留）

```text
玩家输入是什么：玩家的输入是按键，也就是WASD。
移动速度放在哪里、单位是什么：基础移动速度放在配置文件里，然后游戏的类中应该有一个Runtime的速度值，这个会受到当前玩家情况的影响，单位是m/s。
输入如何变成世界位移：输入就是变成一个向量，然后这个向量乘以速度，每帧让受控的人物按照向量移动即可。
```

## 1. 需求一句话（做什么＋本周不做什么）

- 〔助手填〕船长在HarborLab平地上按WASD以固定速度（m/s）沿世界轴移动（W为+Z、D为+X），松开即停，被墙挡住并可沿墙滑动。
- 〔助手填〕本周不做：重力与坡道、相机相对移动与跟随、转向、动画、交互、配置表。

## 2. 移动方式

- 选择：CharacterController.Move。〔助手填〕它不由物理驱动，而是运动学控制：在Move调用内部先做扫掠检测再移动，碰到墙会沿墙面滑动，并带有台阶和坡度限制；没有重力，不受力，所以手感干脆、可精确控制。
- 不选Rigidbody：〔助手填〕Rigidbody由物理驱动，靠力或速度推动，有惯性，会被撞开，逻辑要跟着FixedUpdate走，主角操控不够干脆。它适合需要真实物理反馈的对象，比如以后能推动的木桶。
- 不选直接改transform：直接改位置相当于瞬移，不经过碰撞响应，会穿墙。

## 3. 输入方式2的理由

- 〔助手填〕用户此前用过.inputactions资产，熟悉流程；绑定集中在一个资产里，生成的类有编译期检查，第3周加交互时可以多建一个动作表方便切换。（两种方式底层都是新输入系统，不涉及性能差异。）

## 4. 每帧流程

- 选择：**轮询**。理由：在Update里直接ReadValue最直观，所有逻辑都在一处，不需要处理canceled清零。
- 每帧流程〔助手填·H2，用户要求对照自己的想法〕：
  1. （Update之前）Input System处理本帧排队的输入事件，更新Move动作的当前值。这一步由引擎完成，不写代码。
  2. Update里读取Move的当前值，得到Vector2 `input`，例如W为(0, 1)，W+D待打印确认。
  3. 斜向长度：**待打印确认**。若组合绑定已经输出长度1，就不再处理；否则在这里限制长度。
  4. 映射到世界：`direction = (input.x, 0, input.y)`。输入的y对应世界的+Z，世界的Y保持0，所以平地上高度不变。
  5. 算出这一帧的位移：`motion = direction × moveSpeed × deltaTime`，单位是米。速度单位是m/s，乘以秒后得到米。
  6. 调用`CharacterController.Move(motion)`：在这次调用里完成扫掠检测、遇墙停下或沿墙滑动，返回时位置已经更新。
  7. 没有输入时，input为(0, 0)，motion为零，船长原地不动，即“松开即停”。
- 不在每帧里做的：输入类实例的创建与Enable/Disable/Dispose，放在生命周期函数里（由用户实现时决定）。
- 原先的写法（移动放在performed回调里）已经放弃：按住W时只触发一次回调，船长只会走一帧。

## 架构：三层拆分（2026-10-18 用户决定）

> 决定由用户做出（三层拆分、接口选(a)、命名空间）；以下文字由助手整理〔助手填〕。参考了用户旧项目Zodiac（InputProvider → 状态 → MovementModule）。

**为什么拆**：接舷战中，玩家、3名AI船员和敌人都要移动、都要被墙挡住，区别只在“由谁决定往哪走”。因此移动执行必须与输入解耦，AI的“大脑”以后可以直接复用执行层。

```text
PlayerInputReader ──读取──▶ CaptainController ──速度意图──▶ CharacterMotor ──▶ CharacterController.Move
【输入层】                   【决策层：船长大脑】                【执行层】
                             以后的AI：CrewBrain ──────────────▶ 复用同一个Motor
```

| 类 | 位置 | 负责 | 不负责 |
|---|---|---|---|
| `PlayerInputReader` | `Scripts/Input/` | 持有GameInput并管理其生命周期（创建、启用、禁用、释放）；对外提供`Vector2 Move` | 不知道角色和世界坐标 |
| `CaptainController` | `Scripts/Characters/` | 读取输入，把Vector2映射到世界方向(x, 0, y)，乘以`moveSpeed`得到期望速度，再交给Motor | 不直接调用CharacterController，不乘deltaTime |
| `CharacterMotor` | `Scripts/Characters/` | `[RequireComponent(typeof(CharacterController))]`；`SetMoveVelocity(Vector3 v)`接收期望速度（m/s）；在Update里乘deltaTime，**每帧只调用一次**`Move` | 不知道输入来自玩家还是AI |

- 接口选(a) `SetMoveVelocity(Vector3)`：deltaTime只在Motor里乘一次，与帧率无关的处理集中在一处，“大脑”不需要关心帧率。
- 命名空间统一为`WaveWarlord`。
- 数据：`moveSpeed`（m/s，序列化在CaptainController上，例如5）。基础值与运行时值分离，留到属性系统或配置表时再做。
- 每帧只调用一次Move：以后重力、击退都先在Motor里合并成一个位移再移动，否则多次调用会让`isGrounded`和碰撞结果不准确。
- 后续扩展：Shift奔跑 → Reader增加Sprint，Controller选择速度；第2周相机相对移动 → 改Controller；重力 → 改Motor；12月动画 → Motor对外暴露当前速度。
- 待用户实现时决定：Controller怎样获取Reader和Motor的引用（同一物体上用GetComponent，或者通过序列化字段拖拽）；Update执行顺序是否会造成一帧延迟（审查时讨论）。
